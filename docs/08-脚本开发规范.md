## 1. 适用范围、对象与协议状态

业务脚本可采用 Python、JavaScript、TypeScript、Go、Java、Kotlin、C#、Rust、PHP、Ruby 或其他能在已登记运行环境中执行的语言。平台通过固定制品、进程、JSON 和受控能力交互。语言由运行时适配器扩展，业务输入输出继续由发布者的 Schema 定义。现行 HTTP/HTTPS 业务范围、专属执行环境和三种执行方式沿用架构约定。

开发者按下表确认目标平台支持的协议。

| 对象 | 当前基线 | 本次规范及实施状态 |
| --- | --- | --- |
| 清单 | `contracts/manifest.schema.json` 的 `schema_version=2.0`，language 仅接受 python/nodejs | 保留现行校验入口。增加 manifest 2.1 草案，扩展语言标识和固定运行描述引用 |
| 调用、结果、自定义事件 | 已有2.0 Schema及合成样例 | 多语言继续使用这些信封，通过独立协议协商选择版本 |
| 适配、产物、日志 | 已有独立Schema及静态校验 | 复用已有语义，具体实现按既有验收矩阵接入 |
| SDK、Runner、Guest Agent | 平台目前按2.0清单校验，执行能力以接入方提供的验证清单为准 | 标准SDK、进程桥接、三模式真实执行和景点核验仍需实现及运行验收 |
| 多语言进程桥接 | 当前工程尚无本章桥接实现 | 本章定义 `invocation-files/1.0` 和 `hook-bridge/1.0` 目标协议 |
| 开发交付 | 脚本包、声明契约和验证记录 | 平台完成构建和隔离运行验证后登记可用能力 |

manifest 2.1草案使用新的Schema路径，现行2.0清单仍按原Schema解析。新增语言需要已登记的运行配置、构建工具链、协议能力和对应执行方式验证。语言标识合法仅完成格式校验，调度时还须匹配实际节点能力。

manifest2.1扩展字段及runtime1.0完整示例见第5章。启用草案协议前，编辑器、封存、构建、部署、Runner和Agent必须支持相应能力。现有天安门Python脚本可先采用2.0标准封装。

开发者需要理解以下对象的生命周期。

| 对象 | 含义及使用方式 |
| --- | --- |
| ScriptVersion | 封存的代码、依赖和Schema版本，输入输出按该版本校验 |
| Task | 用户确认的参数、计划及授权配置 |
| Run | 一次逻辑执行，可能包含后续补充信息和接续 |
| Attempt | 一次专属执行环境的尝试，拥有独立目录和租约 |
| Invocation | 一次具体动作调用，其最终Result按invocation_id幂等接受 |
| PendingAction | 当前需要用户更新资料或在外部处理的事项 |
| OutputSeries/Batch | 本次逻辑执行的产物系列和其中一次产出 |

业务代码可报告自己的执行结论。平台根据授权、出站记录及已配置核验器维护外部事实和商业履约。开发者在返回值中明确业务状态及证据来源。

## 2. 接入形态与交付物

| 接入形态 | 使用方式 | 开发者需要完成的工作 |
| --- | --- | --- |
| 标准Hook | Python/Node.js SDK包装器，或实现hook-bridge的其他语言程序 | 注册动作及可选Hook，返回结构化结果，使用统一HTTP、产物和事件能力 |
| 文件协议 | 任意已支持语言的独立进程，使用invocation-files | 读取调用文件，完成一个动作，原子交接结果文件。可通过本地桥接申请公共能力 |
| 既有脚本适配 | legacy入口加adapter 1.0 | 提供参数映射和明确产物路径。需要业务结果时另外生成有效2.0结果信封 |

文件协议采用 `integration_mode=legacy`，保留唯一动作规则，hooks为空。多个独立命令可以分别封装为多个脚本版本。需要在同一版本注册多个动作或声明生命周期Hook时，采用标准Hook接入并实现接受确认后的调用顺序。

交付包包含下列内容，文件名可按工程语言调整，清单中的引用须同步。

```text
package/
  manifest.json
  runtime.json                 # manifest 2.1引用，2.0由现有语言配置启动
  src/                         # 源码及可选协议封装器
  requirements.lock            # 或对应语言的依赖锁与项目文件
  schemas/                     # 可选，本包内固定引用
  fixtures/                    # 可选，脱敏或合成输入和上游响应
  bin/                         # 可选，构建阶段生成的程序
```

包内提供入口、依赖、参数说明、动作、副作用、网络域名、凭据别名和输出契约。外部SDK包版本及模型资源也属于构建输入。包含OCR或本地模型时，在构建期固定模型来源及摘要，并纳入资源预算。

封存前校验文件引用、包大小、路径和摘要。构建制品记录操作系统、CPU架构、运行配置修订、工具链及镜像摘要、依赖锁摘要和产物摘要。依赖在隔离构建阶段准备，业务运行使用封存后的固定制品。源码包和可执行制品各自保存摘要，编译型入口在构建后检查存在和可执行性。

真实Token、Cookie、密码、验证码、HAR、用户config、日志和预约结果通过用户数据入口管理。开发包中的fixtures使用合成数据，便于跨环境重复验证。

## 3. 脚本结构与设计模式

开发者根据实际变化点采用设计模式。一个短小的查询动作可以用函数直接完成。业务增加第二种实现、需要替换外部依赖，或出现跨调用状态恢复时，再增加相应边界。代码优先组合，状态和依赖显式传入。

### 3.1 模块职责

| 模块 | 职责 | 典型接口 |
| --- | --- | --- |
| 协议入口 | 解析Invocation、选择动作、封装Result及调用SDK | dispatch(ctx)、to_result(value) |
| 应用服务 | 编排本次业务步骤、取消检查及错误转换 | preview(ctx)、book(ctx)、query(ctx) |
| 业务规则 | 计算候选方案、校验人员与金额、解释业务状态 | build_plan(input, observations) |
| 外部适配器 | 发送受控请求、处理会话、解析上游结构 | transport.request(request)、provider.query(reference) |
| 状态存储接口 | 保存检查点、读取操作回执及已处理游标 | checkpoints.load/save、operations.get |

协议入口将只读输入和允许能力交给应用服务。业务规则返回普通值，外部适配器承担具体HTTP字段转换。一个模块可以先用函数文件表达，出现多个实现时再定义接口或类。

### 3.2 设计模式的适用场景

| 模式或实践 | 适用条件 | 本系统用法 | 实现尺度 |
| --- | --- | --- | --- |
| 适配器模式 | 本地CLI、SDK、上游接口与平台调用格式不同 | 把Invocation转为业务输入，把requests或语言HTTP客户端接到受控transport，再把业务结果转成Result | 一层输入和输出转换，覆盖所有网络路径 |
| 策略模式 | 日期选择、票种选择或查询退避有多种算法 | 用函数或接口注入TicketSelection、PollPolicy，记录已选择策略 | 同一策略只有一种实现时保留普通函数 |
| 命令模式 | 同版本具有多个独立动作 | 使用action到处理函数的固定注册表，分别声明输入、输出和副作用 | 小规模函数表即可，调用时按注册表精确查找 |
| 状态模式或显式状态机 | 外部写入存在受理、排队、确认、未知和接续 | 用枚举、转换表和纯函数表达允许转移，状态随操作证据持久化 | 转换表适合当前预约流程，复杂状态才拆分状态对象 |
| 依赖注入 | 需要离线测试、更换客户端或控制时间 | 在入口注入transport、clock、wait、operations和logger | 构造参数或函数参数，按需要增加容器 |
| 模板方法的流程思路 | 各动作共享相同初始化、校验、接受确认和清理顺序 | 平台SDK统一执行生命周期，业务实现声明的动作与可选Hook | 业务层使用组合和固定分发，SDK承担调用顺序 |
| 装饰器模式 | 多个适配器共享脱敏日志、计量或只读退避 | 包装transport，在同一请求链路记录耗时和受限错误 | 写入重试由操作效果策略单独决定 |
| 仓储接口 | 多个恢复步骤需要读写同一业务进度 | 定义小型CheckpointStore或OperationReader并适配平台能力 | 本地内存实现仅供测试，生产接口使用平台持久化能力 |

创建用户、发短信、提交预约、发送消息等外部效果各有稳定操作键及授权边界。为HTTP客户端增加通用装饰器时，分别指定只读查询和外部写入的处理策略。通过枚举判断状态时必须保留UNKNOWN分支及原始受限证据。

### 3.3 动作注册与依赖注入示意

下列Python代码展示应用组织方式，ctx和ports由封装层提供。示例中的业务函数属于开发者实现，具体SDK调用签名由后续已发布版本提供。

```python
from dataclasses import dataclass
from typing import Callable, Mapping


@dataclass(frozen=True)
class Ports:
    provider: object
    operations: object
    clock: Callable[[], float]
    wait: Callable[[float], object]
    logger: object


def make_actions(ports: Ports) -> Mapping[str, Callable]:
    async def preview(ctx):
        observations = await ports.provider.fetch_options(ctx.input)
        plan = build_plan(ctx.input, observations)
        return preview_result(plan)

    async def book(ctx):
        return await execute_booking(ctx, ports)

    async def query(ctx):
        return await query_existing_booking(ctx, ports)

    return {
        "preview_booking": preview,
        "book": book,
        "query_order": query,
    }


async def dispatch(ctx, actions):
    handler = actions.get(ctx.action)
    if handler is None:
        raise ValueError("ACTION_NOT_FOUND")
    return await handler(ctx)
```

JavaScript/TypeScript可使用Map及普通对象注入依赖，Go可使用小接口与函数值，Java/C#可使用接口加构造参数。动作名称、输入输出和外部副作用语义在各语言中保持一致。

### 3.4 测试替身与变化范围

业务规则通过合成票种、日期和人员记录测试。FakeTransport返回明确的受理、拒绝、超时和破损响应，FakeClock与可取消wait控制时间，FakeOperationStore模拟已登记和未决操作。增加策略时覆盖策略差异，增加适配器时覆盖协议转换，增加状态时覆盖允许及非法转换。

同一业务流程只保留一个调度与状态推进位置。协议入口负责参数与返回值，策略负责选择，适配器负责传输。跨用户数据通过本次上下文显式传入，跨进程恢复通过平台记录进行。

## 4. 脚本包、清单、自定义动作与输入 Schema

协议2.0定义清单、调用、结果、自定义事件、产物登记与批次。下文给出完整示例和字段约束，业务input/data按发布者Schema二次校验。协议1.0存量版本使用其固定兼容解析器，迁移时发布新ScriptVersion。

有效输入 Schema = `actions[action].input_schema`（若显式存在），否则 `input_schema`。版本 input_schema 始终必填，包括无参数脚本。标准 hooks 模式每个动作有 handler 和 output_schema；legacy 仅一个默认入口动作，可省结构化输出，但不能宣称存在业务结果。动作名在该版本内唯一，平台不维护业务动作枚举。

Schema 使用 JSON Schema Draft 2020-12。首期允许布尔 Schema 与对象 Schema；根业务输入可为任意 JSON 类型。上传时执行方言元校验和平台支持项检查；允许类型、对象/数组/数值/字符串约束、required、enum/const、组合/条件、依赖、局部引用和 $defs。引用仅可解析本包已固定的 Schema，禁止校验期间网络取引用；循环引用、过深结构、超出计算预算或未知校验关键字明确拒绝。发布前编译后端与前端使用的相同 Schema 配置；客户端无法渲染时使用 JSON 编辑器，不能放宽校验。

`default`、`title`、`description`、`examples` 为展示信息；后端不补值、不删字段、不转换类型。平台明确对 `date`、`date-time`、`uri`、`email` 启用格式校验，其余 format 在发布时拒绝，避免客户端与服务端理解不同。正则与输入有大小和执行预算。对 Schema 本身的约束不等于强制业务字段；清单检查器与业务校验器是不同环节。

初始限额：清单含内嵌 Schema 总计 1 MiB，业务 input 256 KiB，结果信封 1 MiB，自定义事件 data 64 KiB；更大产物走对象上传，不塞进结果 data。限额随资源策略公开，发布者 Schema 不可绕过平台资源预算；超限返回明确错误且不回显原值。表单与服务端采用同一限额，业务字段仍完全由发布者定义。

legacy 可附带独立 adapter 1.0 制品配置（不在脚本 2.0 manifest 内增加字段），并由封存索引绑定摘要；必须协商 Runner 能力后启用。它仍受唯一动作、Schema、网络/凭据边界及进程结果语义约束。声明式映射、连续文件交接、有限通知桥接和不支持的能力详见 [旧脚本接入规则](#legacy)。旧脚本的 safe_resume 不从名称、进程循环或桥接能力推断。

| 字段 | 功能要求 |
| --- | --- |
| `schema_version` | 明确协议版本，不兼容时拒绝执行 |
| `script_id`、`version` | 资产和版本标识；服务端同时生成不可变版本 ID |
| `language`、`entrypoint` | 指定语言和包内入口；Hook 模式由 SDK 在执行环境中加载其导出函数，禁止越出包目录 |
| `integration_mode` | `hooks` 标准接入或 `legacy` 兼容运行；使用 Hook 名称不自动提升结果可信程度 |
| `hook_protocol_version`、`hooks` | Hook 模式声明协议版本；hooks 仅登记可选生命周期 Hook，允许空对象 |
| `actions`、`default_action` | 发布者自定义动作注册表及默认动作；每个动作指定处理函数、名称说明、输出 Schema 与副作用声明，不限于平台预设业务枚举 |
| `input_schema` | 每个可执行版本必填，由发布者定义业务输入的字段、结构、类型、必填、枚举、长度及其他受支持约束；平台不追加统一业务字段 |
| `credential_requirements` | 所需凭据类别，不包含真实凭据 |
| `dependencies_lock` | 锁定依赖及构建输入 |
| `network_requirements` | 请求域名和所需网络方式，最终权限由平台策略自动校验及用户授权共同限制 |
| `supported_execution_modes` | 发布者声明支持的执行方式；实际验证证据单独展示，不授予节点权限 |
| `actions.*.input_schema` | 可选完整覆盖版本级 input_schema，缺省继承；不进行隐式合并，最终有效 Schema 仍由发布者定义 |
| `actions.*.output_schema` | 标准 Hook 模式每个动作必填，由发布者定义结果 data 的 JSON Schema；legacy 仅日志运行可省略，不声称有结构化业务结果 |
| `events`、`extensions` | 可选自定义事件定义及显式业务扩展绑定；普通脚本可为空 |

动作名、分类和 `side_effects` 是发布者声明，不是权限证明。动作在脚本版本内注册，不维护全平台封闭业务能力枚举；真正的网络、凭据和资源授权由平台策略控制。

输入参数按以下规则处理：

1. 版本级 `input_schema` 必须提供；动作声明完整 input_schema 时优先使用该定义，否则继承版本定义。具体必填项按有效 Schema 的 required 等约束决定。无参数脚本也须显式定义接受的输入。
2. Schema 随 ScriptVersion 固定。草稿可暂缺 Schema；进入可执行状态、私有测试或服务发布前必须校验 Schema 有效性及平台支持范围，缺失、无效或不支持的校验规则明确报错。
3. 创建、编辑和测试任务时，根据所选版本的 Schema 生成参数表单；`title`、`description` 和 `examples` 用于展示说明。复杂结构无法直接渲染时提供 JSON 编辑入口，仍执行相同校验，不忽略约束。
4. `default` 可以供表单预填，但预填值必须成为用户确认的提交内容；服务端校验不静默补默认值、不转换类型、不删除多余字段。额外字段是否允许以该 Schema 为准。[JSON Schema 对象规则](https://json-schema.org/understanding-json-schema/reference/object)、[注解与默认值](https://json-schema.org/understanding-json-schema/reference/annotations)
5. 前端即时提示，服务端在保存任务、手动测试、触发执行和人工恢复时按绑定版本再次校验最终输入；返回字段路径、规则和可读原因，避免回显敏感参数值。运行使用已校验的参数快照。
6. 修改 Schema 必须创建新版本。用户主动迁移版本时展示字段差异并重新校验；新必填项未填写时不得启用新配置。日期、人数、时段等只是某个发布者可能定义的字段，平台不得要求所有脚本包含它们。

平台运行编号、可空扩展上下文、调度和执行方式属于独立字段；input 仅包含用户按所选动作有效 Schema 提交的参数。旅行场景的预约授权与防重由对应连接器校验，普通自定义任务不要求渠道或预约目标。

## 5. 多语言运行描述

manifest 2.1在2.0清单基础上扩展两处字段。`language`采用小写标识符，`runtime_spec`固定运行描述的包内路径及SHA-256。其他动作、Hook、Schema和授权规则沿用本文件。

| runtime字段 | 开发约束 |
| --- | --- |
| `runtime_protocol_version` | 固定1.0，独立协商 |
| `runtime_profile_id` | 已登记的不可变运行配置ID，平台校验使用权限及可用状态 |
| `platform` | os固定linux，architecture为amd64或arm64，与实际制品及节点匹配 |
| `build.commands` | 可选的命令数组，每条命令又是独立argv数组，在隔离构建环境顺序执行 |
| `launch.argv` | 必填启动argv，程序路径及参数逐项传递，固定引用包内制品或配置内已登记工具 |
| `launch.protocol` | invocation-files/1.0或hook-bridge/1.0 |

运行配置由平台维护语言工具链、确切版本、基础镜像摘要、程序解析规则、构建出口和可用执行方式。发布者选择可用配置。清单中的entrypoint应为最终业务入口，launch.argv包含该入口或启动它的固定dispatcher，构建检查须验证二者关系。执行时的/app为只读制品目录，cwd固定为/app。build.commands也在构建容器的/app工作目录执行。

下面的Go描述为草案示例，runtime_profile_id是合成标识。实际使用须先登记对应运行配置。

```json
{
  "runtime_protocol_version": "1.0",
  "runtime_profile_id": "go-linux-amd64-demo-v1",
  "platform": {"os": "linux", "architecture": "amd64"},
  "build": {
    "commands": [
      ["go", "build", "-mod=readonly", "-trimpath", "-o", "bin/main", "./cmd/main"]
    ]
  },
  "launch": {
    "argv": ["/app/bin/main"],
    "protocol": "invocation-files/1.0"
  }
}
```

| 语言 | 典型构建输入 | 典型启动argv |
| --- | --- | --- |
| Python | 源码、固定依赖及散列锁 | `["python", "/app/main.py"]` |
| JavaScript | package.json、package-lock.json | `["node", "/app/main.mjs"]` |
| TypeScript | 锁文件、编译配置及编译产物 | `["node", "/app/dist/main.js"]` |
| Go | go.mod、依赖存在时的go.sum、源码 | `["/app/bin/main"]` |
| Java/Kotlin | 项目文件、完整固定依赖清单及JAR | `["java", "-jar", "/app/app.jar"]` |
| C# | 项目文件、锁文件及发布产物 | `["dotnet", "/app/app.dll"]` |
| Rust | Cargo.toml、Cargo.lock及源码 | `["/app/bin/main"]` |
| PHP/Ruby | 项目文件及对应依赖锁 | `["php", "/app/main.php"]` 或 `["ruby", "/app/main.rb"]` |

表内命令展示包的入口形式。版本、库可用性、架构和镜像兼容性由具体运行配置及构建结果确定。新增语言复用现有任务、权益、事件和产物协议，运行适配器负责解释器或可执行程序的准备与启动。



manifest2.1的language使用 `[a-z][a-z0-9_+-]{0,31}`。清单中的runtime_spec为 `{path:string,sha256:string}`，path指向包内运行描述，sha256为该文件实际字节的64位小写摘要。build可省略，commands为空数组表示无需额外构建步骤。每条命令和launch.argv含1～64个独立字符串参数，build.commands最多16条。运行配置ID固定确切工具链版本，启动程序通过该配置或/app路径解析。

### 6.1 调用信封

```json
{

  "run_id": "run_demo_001",
  "attempt_id": "attempt_demo_001",
  "invocation_id": "inv_demo_001",
  "script_version_id": "sv_demo_001_v2",
  "action": "summarize_records",

    "source_url": "https://api.example.invalid/records",

  },

  },
  "credential_bindings": [],
```

平台通过脚本版本和动作取得有效输入 Schema，只校验 `input`；运行 ID、模式、凭据绑定和扩展上下文另按平台协议校验。`context` 可以为空，只有显式绑定扩展后才由平台填充对应上下文。业务输入即使使用同名字段，也不能覆盖外层元数据。凭据绑定按发布者需求别名关联本人凭据，匿名动作允许空列表。

平台保留输入 JSON 的原始结构和类型，运行使用已校验快照。发布者可定义完全不同的业务参数；平台不根据字段名称猜测日期、人员或业务含义。输入校验失败在分配执行环境前拒绝，不把原始值写入日志。

### 6.2 文件交接与控制

任意语言的最低接入流程为读取一次Invocation、执行其action、写出一个完整Result。JSON采用UTF-8无BOM编码，只接受有限数值，拒绝NaN、Infinity及重复对象键。金额使用最小币种整数单位。超过跨语言精确整数范围的业务编号和大整数由发布者Schema定义为十进制字符串，业务ID统一保留字符串形态。

| 路径或变量 | 内容及权限 |
| --- | --- |
| `/app` | 本版本只读制品，运行时cwd |
| `TT_INVOCATION_PATH` | 0600只读调用文件，默认/work/input/invocation.json，内容符合invocation.schema.json |
| Invocation的`output_path` | 本次唯一结果路径，位于/work/results，直接读取信封值 |
| `TT_OUTPUT_DIR` | 本次可生成产物目录，默认/work/outputs |
| `TT_TEMP_DIR` | 本次临时目录，默认/work/tmp |
| `TT_CONTROL_PATH` | Agent维护的只读控制快照，默认/work/input/control.json |
| `TT_BRIDGE_URL` | 可选，本环境专属的本地HTTP桥接地址，由平台注入 |
| `TT_BRIDGE_TOKEN_FILE` | 可选，0600内存文件中的短期调用能力令牌 |

TT_*由平台注入，发布者配置使用自己的业务变量名。调用文件只含凭据版本引用。需要明文凭据的能力按[业务参数与凭据](#configuration)绑定交付。敏感文件使用独立目录及访问权限，实际路径由Runner提供。

结果写入采用同一目录内创建唯一临时文件、写完、flush并关闭、原子rename到output_path。同一Invocation至多交接一个逻辑最终结果。Runner只读取已完整交接的普通文件，限制大小、目录、链接和读取竞争，并核对关联字段。文件路径、退出码及stdout均可分别查询。

invocation-files在进程及其子进程停止后采集最终结果。需要过程中的产物和事件时通过本地桥接提交。stdout/stderr保持日志用途。退出0表示进程正常交接，业务可返回COMPLETED、ACTION_REQUIRED或ERROR。未形成有效结果而退出、超时或崩溃时，由平台结合实际出站证据决定失败或未知效果。结果已接受后的进程异常作为执行诊断记录。

`TT_CONTROL_PATH`由Agent原子更新，包含protocol_version=1.0、revision、cancel_requested、stop_requested、deadline及lease_expires_at。脚本在循环、等待和发出新请求前检查。控制文件缺失或持续不可读时停止申请新的业务请求。跨调用恢复使用平台检查点，临时目录和局部内存按本次环境处理。

## 7. 生命周期 Hook、SDK 与调用顺序

以下为待实现的协议，未声称已有可安装 SDK。业务函数由发布者在 actions 中注册，名称不限于平台预设业务；生命周期 Hook 采用固定名称，全部可选。

| 接口 | 返回与用途 | 约束 |
| --- | --- | --- |
| `actions.<name>.handler(ctx)` | 执行任意受支持的自定义 HTTP 业务，返回 outcome、data 等 | 至少一个动作；输入输出按发布者有效 Schema 校验 |
| `on_init(ctx)` | 无返回值，准备本次调用的局部资源 | 可重复执行，不负责主要业务写入 |
| `validate_input(ctx)` | 返回 valid 与脱敏 issues，补充领域语义检查 | 不放宽 Schema，不增加隐藏必填项，不改写输入 |
| `before_action(ctx)` | 无返回值，动作前准备 | 异常阻止本次主动作 |
| `on_outputs(ctx, trigger)` | 无业务返回值；可反复为不同 emission 生成产物 | 可选；运行中/间隔/检查点/final 触发串行处理；受独立 OUTPUT 权限和每次期限约束 |
| `after_action(ctx, result)` | 无返回值，处理已接受结果的副本 | 不能改写已保存结果或触发主动作重放 |
| `on_error(ctx, error)` | 无返回值，记录脱敏诊断 | 保留主错误，不递归调用，不自行申请自动重试 |
| `on_cleanup(ctx)` | 无返回值，释放局部资源 | 尽力执行，宿主回收不依赖其一定运行 |

`check_availability`、`book`、`query_order`、`validate_auth` 可以作为旅行场景动作模板。只有显式选择该扩展时才检查相应动作组合与结果格式；自定义脚本不必实现这些函数。核心不根据动作恰好名为 book 而授予权限或启用订单状态机。

| SDK 上下文 / 能力 | 通用约定 |
| --- | --- |
| `ctx.input` | 对应动作有效 Schema 校验后的只读业务输入快照 |
| `ctx.action`、运行关联字段 | 本次注册动作、Run、Attempt、Invocation、脚本版本及租约引用 |
| `ctx.context`、`ctx.runtime` | 可空扩展上下文、执行窗口、运行模式；实际授权取自服务端记录 |
| `ctx.http.request(request)` | 通用 HTTP/HTTPS 请求，允许在批准的网络与凭据范围内自行构造方法、URL、请求头和请求体；不要求平台为每种业务实现连接器 |
| `ctx.connectors.invoke(operation, payload)` | 可选已注册的可信领域操作；使用该扩展时才需要对应操作定义与授权 |
| `ctx.logger` | 受限结构化日志，进入统一脱敏与配额链路 |
| `ctx.checkpoint` | 本任务范围的检查点读写，不提供任意数据库或文件系统管理能力 |
| `ctx.events`、`ctx.notify` | 提交已声明事件和通知请求，由平台校验订阅、去重和投递 |
| `ctx.outputs` | batch/collect/text/json/file/bytes/message/get；多格式输出与每批幂等，可在同 Run 多次提交 |
| `ctx.artifacts` | 旧文件输出适配接口，新实现统一走 outputs 的上传、校验、权限与保留 |
| `ctx.progress`、`ctx.wait` | 持续任务进度及可取消等待；运行心跳由 Runner/Agent 独立维持 |
| `ctx.signal`、`ctx.deadline` | 协作取消与截止时间，Runner 另行实施硬限制 |
| `ctx.state` | 同一次调用的 Hook 之间共享临时对象，不保证跨调用或恢复保存 |

函数名、SDK 只读对象及发布者声明不能作为安全边界。任意业务逻辑仍在任务专属容器或客户机中执行；通用网关检查实际网络目标、凭据绑定与预算，平台不直接执行用户提供的业务解析代码。请求体可以是发布者自定义结构，不要求统一旅游字段；是否符合某项业务授权由主动绑定的领域连接器另行判断。

### 7.1 唯一调用顺序

1. 控制面校验版本、动作、完整输入、权限、窗口与并发；固定 Schema 摘要及输入摘要。
2. 领取租约并准备环境；SDK 加载代码后执行可选 `on_init → validate_input → before_action`。
3. 执行所选 `actions.<name>.handler(ctx)`；平台不额外调用查票或预约函数。
4. SDK 提交结果；服务端校验信封、注册动作、实际归属及 data Schema，持久化接受记录。
5. 运行期间可通过 collect/batch 多次产出；SDK 得到最终结果接受确认后可触发一次 final `on_outputs(ctx, trigger)` 并提交对应批次；随后执行 `after_action`，最后尽力 `on_cleanup`。产物 Hook 不改业务结果；前置/主动作异常只调用一次 on_error，不递归，若能形成有效 ERROR 结果仍可按授权生成错误报告。
6. 宿主独立停止并回收环境。进程崩溃、强杀、失联不保证任何末尾 Hook 执行。

on_init/before_action/validate_input 不承担主要外部写入；after_action/on_error/on_cleanup 不追加主要业务副作用或修改结果。它们仍是不可信代码，网关不能仅凭 Hook 名证明安全。结果接受后撤销业务出站能力，仅保留有界结果回执/诊断及专用 OUTPUT 上传登记权限；运行中 on_outputs 的临时阶段切换则按第12章的产物阶段规则暂停业务许可，返回后重新校验并恢复；Hook 本身不取得业务 HTTP 或凭据访问；需要可靠后续业务操作时应在主动作完成前执行，或显式创建下一业务调用。

一次 Run 选择一个注册动作，动作内可以执行多个 HTTP 请求。可选业务扩展可明确编排多次调用，每次独立 Invocation 并持久化推进状态；核心不因动作名称为 book 自动启用旅行流程。跨 Attempt 不依赖 Hook 临时内存。
<a id="configuration"></a>

## 8. 业务参数、凭据与配置

开发者先定义input_schema和每个动作的output_schema，再实现代码。必填、默认值、类型、空值、额外字段和动作覆盖规则按第4章处理。语义校验用于日期范围、人数、授权选择、枚举之间的关系及上游约束，返回脱敏字段路径。有效输入是不可变快照，动态上游响应保存在本次临时状态中。

| 数据 | 保存和传递方式 |
| --- | --- |
| 日期、查询目标、业务选项 | 发布者input_schema，按用户确认后的完整input传入 |
| 姓名、手机号、证件、人员选择 | 本人敏感输入或已绑定领域快照，持久化加密，展示按权限掩码 |
| Token、Cookie、密码 | manifest凭据别名加用户credential_binding，固定凭据版本 |
| 验证码、临时挑战 | 用户待处理或专用挑战入口，有效期及单次消费约束 |
| 调度、期限、资源、重试、通知渠道 | 平台任务配置和授权，信封中提供有效运行上下文 |
| 供应商固定域名、协议常量 | 脚本代码或版本固定的业务配置，并在network_requirements声明 |
| 服务费、权益、退款、结算 | 平台服务及交易对象，由固定成交规则处理 |

凭据kind的支持列表和secret_payload结构由凭据服务登记。新kind需要明确字段、敏感范围、适用域和轮换行为。读取接口仅在已授权的解密交付形态启用，能够使用网关代注入的凭据可通过credential_alias调用。以Cookie或凭据版本更新接续时重新绑定并校验用户身份，现有Invocation保持自己的凭据快照。

交互流程生成ACTION_REQUIRED，释放环境后由用户通过页面处理，再创建新的Invocation接续。参数Schema保持版本固定，恢复动作有独立输入。需要发送短信、登记人员、更新密码等外部写入时，单独声明相应动作和授权范围，并遵循写入效果处理规则。

<a id="side-effects"></a>

## 9. HTTP、副作用与重复执行

开发者为每个动作声明side_effects，为每个请求声明实际效果类别。查询接口可能使用POST，外部写入也可能隐藏在GET中，平台和脚本须按接口业务行为及核验结果共同判断。

外部写入前保存操作意图和稳定的操作键。平台网关持久化请求登记、可能发送的状态及回执，操作键绑定逻辑履约和业务目标，跨Attempt及人工接续可关联同一业务意图。归属、防重和操作锁通过平台授权及效果记录约束。检查点和进程内锁用于进度管理，恢复前还要核对平台出站记录。

| 请求结果或故障 | 下一步 |
| --- | --- |
| 明确只读查询失败 | 在期限、额度和限流允许范围内退避重试 |
| 请求在授权检查阶段被拒绝，已证明未发送 | 修正配置或在有效授权和预算内重新请求 |
| 外部系统支持且已经验证其幂等协议 | 使用同一上游幂等键查询或按该协议重传 |
| 外部写入已接受，得到排队号或taskId | 保存接受证据，后续查询该操作 |
| 写入发生读取超时、连接中断、5xx或无法解析响应 | 保存UNKNOWN，停止该意图的继续提交，进入独立查询或本人待处理 |
| 明确业务拒绝且证据表明未受理 | 在渠道规则、次数和当前授权内调整或重试 |
| 未知业务码、含糊的“繁忙/排队/稍后”提示 | 保存原始受限证据，查询现有操作，无法确认时保留UNKNOWN |
| 结果已接受、产物或通知失败 | 查询或重传对应回执，使用原结果或批次键修复交付 |

同一次逻辑预约的日期替代、时段替代、人员变化和金额上限必须在已确认授权内。发生未决写入时保留防重阻塞。外部接口缺乏幂等键时，平台仍可能遇到“请求已发出、回执尚未落库”的故障窗口，按照UNKNOWN处理并保留核验入口。

## 10. 结果、回执与待处理协议

```json
{
  "protocol_version": "2.0",
  "run_id": "run_demo_001",
  "attempt_id": "attempt_demo_001",
  "invocation_id": "inv_demo_001",
  "action": "summarize_records",
  "outcome": "COMPLETED",
  "summary": "已汇总 1 条记录",
  "data": {
    "item_count": 1,
    "records": [
      {
        "id": "record_demo",
        "status": "active"
      }
    ]
  },
  "action_required": null,
  "error": null,
  "outputs": []
}
```

| 字段 | 约定 |
| --- | --- |
| `outcome` | COMPLETED、ACTION_REQUIRED、ERROR；表示协议执行结果，不保证外部业务事实已核验 |
| `data` | COMPLETED 时必须符合该动作发布者 output_schema；其他 outcome 可为 null，非 null 时仍校验 |
| `summary` | 可选、限长且脱敏的纯文本说明，不执行 HTML/JS |
| `outputs` | 接受时的引用快照，来自当前授权产物系列已提交项或末尾 ACTION 批次；后续/历史通过独立集合分页查询，不嵌入文件正文或任意下载地址 |
| `action_required` | ACTION_REQUIRED 时必填，包含允许的处理类型、说明、期限和恢复动作；恢复动作必须属于该版本注册表，仍需权限与参数校验 |
| `error` | ERROR 时必填，包含代码、脱敏消息及有限详情；不能由脚本决定平台自动重试 |
| 运行关联字段 | SDK 封装，服务端与实际派发记录核对，脚本自报值不能覆盖归属 |

通用界面按 Schema 展示自定义 data，至少提供 JSON 与摘要视图。数据格式有效与业务真实性分开，通用脚本结果默认标明来自脚本报告。需要 VERIFIED 等领域事实时由已绑定扩展的可信核验器处理，普通脚本不用返回 availability、booking 或任何特定业务结构。

Hook 模式由 SDK 封装结果并提交，开发者无需管理结果文件。文件通道按 Invocation 分配独立路径，检查大小、越界和符号链接；兼容模式按独立执行分配路径。stdout/stderr 仅为日志。平台收到并持久化有效结果后返回接受确认，重复结果按调用 ID 幂等；矛盾结果报告协议错误，不覆盖已接受事实。

### 10.1 待处理与多次调用

| outcome | data | action_required / error | 平台行为 |
| --- | --- | --- | --- |
| COMPLETED | 必须通过 output_schema；允许 Schema 明确接受的 null | 均为 null | 保存脚本报告；没有未决效果且流程已完成时 SUCCEEDED |
| ACTION_REQUIRED | null 或通过 output_schema | action_required 必填，error 为 null | 建立 PendingAction，释放环境并阻塞后续触发 |
| ERROR | null 或通过 output_schema | error 必填，action_required 为 null | 无未决效果时 FAILED；否则核验或转人工 |

`action_required` 含 reason、instructions、expires_at、resume_action。resume_action 可为 null（仅外部处理/人工说明），非空时必须在当前动作的 `resume_actions` 声明和该版本注册表中；其网络与凭据权限重新授权，不能通过恢复扩大原授权。恢复动作输入以该动作固定 Schema 为准，不接受结果临时追加必填业务字段。

action_required 是创建待处理项的请求，不是直接修改 Run 的授权。平台可缩短期限、拒绝非法跳转或将未知副作用限制为核验。外部链接需校验协议与目标策略，页面不执行发布者 HTML/JS。

新结果的 `outputs` 仅为接受时的引用快照（本授权系列已提交项或一个末尾 ACTION 批次），不存文件正文或任意下载 URL，也不要求包含全部历史。运行中和 final Hook 都可产生独立批次，结果信封不改写。`on_outputs` 和 `ctx.outputs.batch/collect/text/json/file/bytes/message/get` 的完整输入、阶段、错误、格式、状态及权限见[旧脚本接入规则](#outputs)。业务 input_schema 与 output_schema 不因产物功能改成固定业务结构。


平台接受结果时原子保存Result及其待处理事项，返回接受回执。已发布阶段批次保持自己的回执，末尾批次按本次接受事务处理。开发者收到接受确认后执行末尾Hook，回执丢失时查询原Invocation。

### 10.2 错误与恢复约定

result的run_id、attempt_id、invocation_id和action从收到的调用信封原样关联。自定义业务状态放data，固定outcome按第10章取值。ERROR包含稳定业务错误码及脱敏原因。COMPLETED的数据也须表达实际业务情况，例如查询完成但无库存。

待处理reason使用现有四个枚举。凭据到期用CREDENTIAL_UPDATE，补业务参数用INPUT_UPDATE，用户在外部完成操作用EXTERNAL_ACTION，效果无法确认用MANUAL_RESOLUTION。expires_at使用实际任务窗口、挑战期限或渠道证据计算，resume_action须已在动作的resume_actions中声明。人工恢复提交该动作完整新输入，原始调用及结果保留。

建议脚本提供稳定错误码，如AUTH_EXPIRED、INPUT_REJECTED、UPSTREAM_RATE_LIMITED、UPSTREAM_UNAVAILABLE、UPSTREAM_RESPONSE_INVALID和WRITE_EFFECT_UNKNOWN。业务错误码放error.code，平台重试根据效果证据和任务策略决定。原始响应先按字段白名单整理，需要保留的受限证据由平台存储及权限控制。

<a id="events"></a>

## 11. 检查点、进度、自定义事件与通知

检查点只保存允许的业务进度，绑定账号、脚本版本、动作和任务，限制大小并加密；不能保存整个进程内存或跨用户恢复环境。读取旧检查点必须验证版本及动作兼容性。检查点不能充当外部操作已成功或可安全重试的证明。

开发者可在 `events` 注册自定义事件及数据 Schema，通过 `ctx.events.emit(name, data)` 或 `ctx.notify.request(...)` 请求通知。服务端校验当前调用、事件声明、数据、用户订阅、收件范围和限额，持久化后进入统一投递链路。去重作用域包含用户、脚本版本、调用、事件及事件键，不能接受脚本任意指定其他用户或邮件地址。事件传输允许重投，跨多次调用的业务去重由用户策略及发布者事件键共同确定。

自定义事件在脚本作用域内命名，界面标明来源；名称相同也不能覆盖平台错误、权限、审计或已核验业务事件。原始参数、凭据不自动进入通知。自定义事件不会自动触发其他脚本或重跑当前动作；外部事件触发与通用 DAG 编排需要另行确定范围。

`ctx.progress.report(stage, cursor_summary=None)` 上报有界脱敏进度，`ctx.wait(seconds)` 可被取消；它们不替代 Runner/Agent 心跳。`ctx.checkpoint.save(value, expected_revision=n)` 只保存检查点，不宣称与此前产物原子提交。需要同步交接时使用 `out.commit(checkpoint=value, expected_checkpoint_revision=n)` 或同参数的 outputs.collect；平台将本批产物提交和检查点CAS置于同一事务，同键重放先返回原回执，再处理新提交的revision检查，成功时两者一起可见。
<a id="outputs"></a>

## 12. 产物、批次与消息

### 12.1 可多次调用的产物 Hook

发布者可声明 `on_outputs(ctx, trigger)`，每个产出触发对应一个独立批次。trigger 包含 emission_id、batch_key、sequence、reason（explicit/interval/checkpoint/final）、snapshot、result、deadline。运行中 result=null；final 触发携带已经接受的最终业务结果。snapshot 是发布者提供的本次数据，不改写业务 input 或伪造最终结果。

脚本可反复调用 `await ctx.outputs.collect(batch_key, snapshot=...)` 执行 Hook；也可以通过批次公共方法直接输出，不必实现 Hook。可选间隔触发由 SDK 在可让出的安全点串行处理，队列有界、积压合并，不并发调用同一脚本的产物 Hook、不强行中断业务函数。Hook 内嵌套 collect 拒绝，避免递归。每个独立 emission 最多派发一次，但新的 emission 可不断触发。

运行中发布的批次即时进入产物及通知链路，界面标为阶段性产出；它们不结束 Run，也不表示业务已最终成功。主动作结束后的顺序为：接受最终结果及可选末尾 ACTION 批次 → final on_outputs → after_action → on_cleanup → 宿主回收。没有 Hook 或产物不影响原执行流程。

Hook 阶段使用独立 OUTPUT 权限，允许本系列产物操作和平台通知登记，不授予业务 HTTP、连接器或凭据解密。持续执行中切换到 Hook 前，受信任 Runner/网关暂停主动作出站许可并使旧业务令牌失效；等待已登记请求收敛，不能收敛则延后触发或报告 OUTPUT_PHASE_BUSY，不据此认定外部请求失败。Hook 返回后只在租约、账号和任务权限仍有效时发放新的业务许可；final Hook 后不恢复业务许可。直接在主动作使用批次方法不切换阶段，仍受原业务权限约束。函数名和 ctx 对象本身不是安全边界。

每次 Hook 有独立有界 deadline，初始预算 30 秒；持续脚本不会因首次产物 deadline 到期而终止。后台没有可抢占的安全点时，间隔 Hook 可延迟并显示延迟状态，不能宣称按间隔必然准时执行。Hook 失败只影响本次批次，默认继续主动作；显式 output_failure_policy=stop 可请求受控停止，不自动重跑业务。

批次和接受回执丢失只重传已持久化内容/查询回执。默认不重新执行同一 emission 的 Hook；生成失败可使用新的 emission 请求重新生成，必须具有当前授权、输入快照及独立产物权限，不重跑主动作。节点失联且原内存/文件未持久化时明确说明内容不可恢复。最终业务结果接受后的 Hook 失败也不能反转业务结果。

### 12.2 SDK 方法

下表为待实现 SDK 的公共方法。on_outputs 中 ctx.outputs 已绑定本次 emission；主动作可通过 `async with ctx.outputs.batch(batch_key) as out` 建立批次，out 提供相同 text/json/file/bytes/message/get 方法，正常退出提交，异常退出保留明确失败并回收未提交项。显式 `await out.commit(checkpoint=..., expected_checkpoint_revision=...)` 可提前提交本批次；提交后继续输出须创建新批次。after_action/on_cleanup 不再生成正式产物。

| 方法 | 参数 | 返回与作用 |
| --- | --- | --- |
| `ctx.outputs.batch(batch_key)` | 稳定批次键 | 批次上下文/句柄；同 key 查询原状态，新 key 开始一次新产出 |
| `ctx.outputs.collect(batch_key, *, snapshot=None, checkpoint=None, expected_checkpoint_revision=None)` | 触发键、本次数据和可选原子检查点 | 串行执行本次 on_outputs，提交/返回独立批次回执；可以多次调用 |
| `ctx.outputs.text(key, text, *, title=None, media_type="text/plain")` | 稳定 key、字符串；支持 text/plain、text/markdown | OutputRef；保存文本并支持 UTF-8 下载 |
| `ctx.outputs.json(key, data, *, title=None)` | 稳定 key、任意合法 JSON 值 | OutputRef；保存结构化内容，可下载 JSON；不要求旅游字段 |
| `ctx.outputs.file(key, path, *, file_name=None, media_type=None, title=None)` | 本次允许输出目录中的普通文件路径；可指定下载名和 MIME | OutputRef；SDK 流式上传，平台校验实际字节与摘要 |
| `ctx.outputs.bytes(key, content_or_stream, *, file_name, media_type="application/octet-stream", title=None)` | 字节数组或有界流，不把 base64 塞进业务结果 | OutputRef；用于动态生成文件或无法先落盘的内容 |
| `ctx.outputs.message(key, *, title, body, channel_binding_ids=None, format="text/plain", attachments=[])` | 消息内容、本人已绑定渠道 ID、已有 OutputRef | OutputRef；持久化消息，满足条件后进入统一通知链路 |
| `ctx.outputs.get(output_id)` | 本次调用允许访问的已登记 ID | 当前状态、大小、摘要和回执；不返回其他用户对象 |

`key` 在 batch 内唯一；相同文件名或 key 可出现在不同 batch。batch_key 在 output_series_id 内唯一，同一 batch/key 同内容返回原引用，异体报冲突。不同 batch_key 表示新的真实产出，即使字节相同也可以再次通知。受控接续复用系列及稳定业务批次键，可防止已提交批次在重启后重复推送；新任务/配置使用新系列，不自动跨用户/跨任务去重。

`channel_binding_ids=None` 表示读取任务已确认的默认通知绑定，由 SDK 解析成明确 ID 后提交；没有默认绑定返回 CHANNEL_BINDING_REQUIRED。明确空数组不是“全渠道”，应拒绝。脚本不填写任意收件地址、Webhook URL 或设备令牌。用户配置、校验和停用渠道的操作独立于业务 input；脚本可以选择其授权范围内的绑定。

兼容说明：旧 `ctx.artifacts` 文件接口适配为 file/bytes，保留既有文件归属限制；旧 `ctx.notify.request` 走同一消息登记与去重服务。`ctx.events.emit` 仍是自定义事件，不会与同 key 的 message 自动合并；开发者选择一种通知来源或配置明确去重策略，避免同时订阅事件又重复发送消息。legacy 可使用 SDK 包装器产物能力，未接入时保持仅日志行为，不自动扫描整个目录当作输出。

<a id="output-contract"></a>

### 12.3 产物声明与必需项

发布者可在 `actions.<name>.output_contract` 声明 `required_keys`、`allowed_kinds`、`max_items`，均随版本固定且不能扩大平台限额。不声明时 required_keys=[]、允许四种 kind、max_items=100。required_keys 按每个声明 scope 的批次检查：output_contract.required_scope=batch（默认）或 final。不同批次可反复使用相同必需 key，不实施整个长任务唯一；final scope 只在最终 emission/末尾批次检查。未产生任何批次而声明 final 必需项时，在结束时明确报缺失。

<a id="output-formats"></a>

### 12.4 格式、文件处理与产物限额

| 形式 | 示例 | 首期平台行为 |
| --- | --- | --- |
| 文本与数据 | TXT、Markdown、CSV、JSON、JSONL、XML、YAML、日志片段 | 文本/JSON 安全预览；其他可作为文件下载，超大内容截断预览 |
| 办公及报告 | PDF、DOCX、XLSX、PPTX | 保存原文件并下载；没有预览能力时明确显示“下载查看”，不承诺在线编辑或转换 |
| 图像 | PNG、JPEG、WebP、GIF、SVG | 受支持的栅格图像可预览；SVG 默认附件下载，不执行其活动内容 |
| 音视频 | MP3、WAV、MP4、WebM | 原文件下载；可选支持的浏览器媒体预览，不默认转码 |
| 压缩与二进制 | ZIP、GZ、任意自定义扩展名/二进制 | 保留字节、摘要和下载名；不自动解压、运行或安装 |
| 通知消息 | 纯文本、受限 Markdown、附件链接 | 站内与邮件首期可用；其他渠道走注册适配器，不限制脚本业务类别 |

文件类型不是封闭业务枚举。扩展名未知时允许以 application/octet-stream 保存下载；不因为平台不会预览而要求修改脚本业务。MIME 与文件名只是声明，服务器检查实际大小、摘要、基础类型一致性及平台策略，不据扩展名执行内容。HTML/脚本/带活动内容格式默认下载，预览在隔离域或安全渲染器中进行，不共享业务页面执行上下文。

初始可配置限额：单文件 100 MiB、单批次文件总量 500 MiB、单批次最多 100 个产物、文本/JSON 单项 1 MiB、消息正文 16 KiB、标题 200 字符、单消息附件最多 10 个。按 UTF-8 实际字节计正文/JSON 限额；持续任务按批次、账号日预算、总存储、产出速率和并发上传分别限额，不设置“整段长期运行只能有 100 个产物”。用户剩余额度、租约时间和上传期限仍可进一步限制，SDK 上传前提示、服务端持续计量。超限明确失败，不能占满磁盘后才发现。

文件入口默认位于 `/work/outputs`，拒绝越界、路径穿越、符号链接、设备文件和管道；Windows/宿主路径不得成为下载地址。文件打开后按文件描述符读取并复核元数据，避免检查路径后被替换。字节流执行等价大小/摘要校验。输入、输出数据与文件内容按用户私有数据加密存储，不默认写日志或发送到外部通知。

### 12.5 产物错误与取消反馈

| 错误/场景 | 处理 |
| --- | --- |
| OUTPUT_KEY_CONFLICT / OUTPUT_BATCH_CONFLICT | 409；查询原回执，禁止覆盖已发布内容 |
| OUTPUT_SCHEMA_INVALID / OUTPUT_REFERENCE_INVALID | 422；提示字段/引用类别，不回显文件正文 |
| OUTPUT_TOO_LARGE / OUTPUT_QUOTA_EXCEEDED | 413/429；停止读取/上传，释放本会话未使用预算；不重跑主动作 |
| OUTPUT_PHASE_CLOSED / OUTPUT_PERMISSION_REVOKED | 409/403；禁止新增，已接受对象保留原记录或按注销流程清理 |
| UPLOAD_CHECKSUM_MISMATCH / UPLOAD_EXPIRED | 422/410；只重传仍授权且可恢复的内容，不能伪造完成 |
| CHANNEL_BINDING_REQUIRED / CHANNEL_BINDING_UNAVAILABLE | 422/409；用户绑定/启用允许渠道，脚本不自行创建收件人 |
| DEPENDENCY_UNAVAILABLE | 消息失败并列出本人可见附件原因；不发送坏链接，不自动删其他成功产物 |
| 结果已接受后 Hook 超时/崩溃 | 生成阶段失败/部分完成，业务结果不变；宿主继续回收 |
| 取消、冻结、注销或版本撤销 | 撤销相应生成/上传/投递权限；停止未开始 Hook；在途上传回执可核对，不能以补传重新获得执行权限 |

### 12.6 开发者产物示例

以下为待实现 Python SDK 的接口示意；`ctx.outputs` 由平台提供，不是本仓库已发布的软件包。业务参数来自脚本自己的 Schema，通知渠道来自用户配置。下面的 fetch_next_page/make_csv_bytes 是开发者业务函数；ctx.wait 为可取消等待，collect 同事务提交本批产物及检查点。示例为接口伪代码，没有连接真实来源。

```python
async def watch_records(ctx):
    cursor_record = await ctx.checkpoint.load()
    while not ctx.signal.cancelled:
        page = await fetch_next_page(ctx.http, ctx.input, cursor_record.value)
        if not page.changed:
            await ctx.wait(5)  # SDK 可中断等待，不忙轮询
            continue
        receipt = await ctx.outputs.collect(
            f"page.{page.stable_id}", snapshot={"records": page.records},
            checkpoint=page.next_cursor,
            expected_checkpoint_revision=cursor_record.revision)
        cursor_record = await ctx.checkpoint.load()  # 重投旧批次也不回退当前游标
    return {"outcome": "COMPLETED", "data": {"stopped": True}}

async def produce_report(ctx, trigger):
    if trigger.reason == "final":
        summary = await ctx.outputs.text("summary", "持续执行已结束")
        await ctx.outputs.message("notice", title="执行已结束",
                                  body="末尾产物已保存。", attachments=[summary])
        return
    records = trigger.snapshot["records"]
    report = await ctx.outputs.json("records", records)
    csv_file = await ctx.outputs.bytes(
        "csv_report", make_csv_bytes(records),
        file_name="report.csv", media_type="text/csv")
    await ctx.outputs.text("summary", f"本批 {len(records)} 条记录")
    await ctx.outputs.message(
        "notice", title="本批报告已生成", body="请登录平台查看。",
        attachments=[report, csv_file])
```


清单将 `hooks.on_outputs` 映射为 `produce_report`，两个方法可在整个 Run 中反复触发多个批次。生成 XLSX/PDF/图片等文件时，开发者先用锁定依赖在 `/work/outputs` 写文件，再调用 file；无须平台为每个扩展名新增业务 API。文件生成所需额外外部数据应在主动作阶段获取并按预算保存，不能在产物 Hook 中重新调用业务接口。

<a id="continuous-config"></a>

## 13. 调度、取消与持续恢复

持续运行配置包括 run_mode、restart_policy、可选 max_uptime_seconds、stop_grace_seconds、output_failure_policy、可选 output_interval_seconds 和 idle_policy。interval 仅决定产物 Hook 请求频率，不是创建新 Run 的 Cron。具体秒数受管理员最小间隔/资源策略限制，积压合并且可观测。

runtime 包含 run_mode、deadline、lease_expires_at、output_deadline、output_series_id 及请求/实际模式。finite 的业务和末尾期限有界；continuous 业务/产物流总期限可空，但当前租约与每次 Hook/上传期限不能省略。恢复要求动作声明固定的 resume_handler 与 checkpoint_schema；普通 legacy 不从循环或通知桥接推断恢复能力。safe_resume启用时，接续必须先读取检查点和既有外部操作，核对当前授权及版本后再推进。

任务启动时间由平台schedule控制。脚本根据当前动作需要进行有限轮询或使用continuous长期驻留。放票目标使用明确日期、时刻和timezone，平台deadline、授权到期与租约约束始终有效。执行上限取这些有效期限中最早者，租约续期读取Agent最新control快照，Invocation中的初始租约供启动校验。内部相对等待使用单调时钟并响应取消。上游Date头仅作为带有精度误差的时钟参考。

每次网络请求有连接、读取和整体时间预算，循环有次数或期限限制，并发受资源配置和目标域名预算控制。大文件采用流式处理。收到stop/cancel、凭据撤销或租约到期时停止申请新业务请求，处理已登记请求的回执，并在有界宽限期内保存进度。平台负责硬限制及进程树回收。

恢复入口需要checkpoint_schema、resume_handler和明确的安全恢复策略。恢复先检查版本、动作、游标、外部操作及已交付产物，再从可证明安全的步骤继续。普通legacy按既有restart_policy=never处理。人工补凭据后的新Invocation也须查询上一次外部操作。

一个消费者任务只能使用本人本次授权的数据。发布者部署固定代码和可复用只读依赖，每个Attempt的可写目录、会话、凭据和网络能力独立。需要在单个Run中处理多个本人授权目标时，开发者明确批次状态与部分完成语义。

<a id="legacy"></a>

## 14. 已有脚本适配与有限青龙兼容

标准 hooks 脚本继续使用脚本协议 2.0。legacy 仍只有一个默认动作；可在封存包中附带 legacy-adapter.schema.json 所描述的配置，独立 `adapter_protocol_version=1.0`。不修改脚本协议 2.0，也不向其严格 manifest 增加未知字段。

发布服务将适配文件登记到封存制品索引，固定 `adapter_path`、`adapter_digest`、`adapter_protocol_version`、`source_digest`、`manifest_digest`、`runner_adapter_digest`。无适配登记的旧版本保持原行为，Runner 不根据目录中存在某个文件自行启用适配。构建、调度和 Agent 均检查能力 `legacy-adapter/1.0`；不支持时在派发前拒绝，不能降级忽略参数、文件或通知。

| 配置 | 语义 |
| --- | --- |
| `action` | 必须等于 legacy manifest 的唯一 default_action |
| `argv` | 参数 token 数组；每项为固定 literal 或 input 的 JSON Pointer 与 encoding，不含解释器/入口，禁止 shell=true 或模板 eval |
| `env` | 显式变量名映射；来源为 input 或已声明并由本人绑定的 credential_alias |
| `config_files` | 从 input 的 JSON Pointer 生成 JSON 文件，路径相对 `/work/input`；0600、独立目录、只读交付脚本 |
| `outputs` | none、final 指定文件清单，或 manifest 连续交接；不扫描整个工作区 |
| `notification_bridge` | disabled 或 qinglong_subset；只启用逐项选择的通知方法 |

解释器由固定镜像和 manifest.language 选择，程序入口由 manifest.entrypoint 选择；参数单独传递。副作用声明与真实出站授权仍由 manifest/任务控制，适配不能授予额外权限。包内入口、锁文件及适配路径都不能越界。

能力页分别显示输入映射、日志、文件产物、通知、结构化结果、检查点恢复的实际支持情况。附加适配不自动获得结构化结果；有效结果必须通过原 2.0 协议和发布者 output_schema 校验。没有结构化结果时只显示 PROCESS_EXIT。普通 legacy 不具备合格 resume_handler，restart_policy 固定 never；希望安全恢复须发布标准 hooks 封装版本并实现既有恢复契约。

### 14.1 参数、环境与依赖边界

先按发布者有效 Schema 校验原 input，再进行映射；映射是传输编码，不改变原输入、必填规则或保存的类型。JSON Pointer 按 RFC 6901 解码，空串指向根；不存在与值为 null 分开。argv 映射可带 `flag`，有值时生成相邻的标志和值两个 token，缺失时整组省略，避免留下孤立选项；无 flag 的可省略位置参数须由发布者确认入口语义。`on_missing=omit` 省略该参数组/变量/文件；`error` 产生 ADAPTER_MAPPING_ERROR，不能由适配配置新增隐藏的用户必填项。发布检查须证明 error 对应路径在所有允许输入分支存在；无法证明时要求 omit 或由发布者显式修改 Schema。

`encoding=string` 只接受字符串；`json` 将任何合法 JSON 值编码一次为紧凑 JSON，布尔值/数字不被猜测成字符串类型。argv 中 `$()`、反引号、空格、引号都作为普通参数字符，不经过 Shell。argv 不接受 credential_alias；含敏感业务字段的输入必须映射到受限文件或凭据绑定，不能展示到命令预览和进程参数。

env 不继承全站或宿主业务环境。系统只注入平台固定并自动校验的基础环境与本次租约上下文；发布者不能覆盖 PATH、HOME、TMPDIR、PYTHONPATH、PYTHONHOME、PYTHONSTARTUP、NODE_OPTIONS、NODE_PATH、LD_*、DYLD_*、TT_* 等执行/加载器变量。变量重名拒绝，不以覆盖顺序解决。凭据 alias 必须在 manifest 声明并由该用户授权绑定，缺失可选绑定仅在 omit 时省略；值带 NUL 或超过编码预算拒绝。密钥轮换不在运行中的进程里静默替换旧环境；旧授权失效时按撤权流程处理。

config_files 路径只能是受控相对路径，不允许 `..`、绝对路径、反斜杠、设备或链接；重复和父子路径冲突均拒绝。首期只生成 JSON，不处理 Shell/YAML 模板表达式。参数映射的完整JSON示例见本章14.4。映射总大小建议 1 MiB，单变量建议 32 KiB，仍服从系统进程参数实际限制。

### 14.2 Hook、通知桥接与文件交接

标准脚本中心提供 on_init/before_action/on_outputs/after_action/on_cleanup 模板以及每阶段测试反馈，Hook 可选且随版本封存。旧脚本若需要自定义前后处理，可由开发者封装为标准 hooks 脚本；首期兼容描述文件不接受任意 task_before/task_after Shell 字符串。前置失败不运行主动作；已接受结果后的后置失败只记录阶段错误。

通知桥接是本项目拟实现的有限兼容层：JS `sendNotify.send(title, content)`、Python `notify.send(title, content)`、JS/Python `QLAPI.systemNotify({title, content})`。只能使用匹配语言且在配置中显式列出的入口；已有同名模块冲突时要求发布者迁移导入路径或明确替换，不能悄悄覆盖依赖。未列签名、第三个配置参数、notificationInfo、任意收件人及 QLAPI.getEnvs/createCron/runCrons 等管理方法返回 ADAPTER_UNSUPPORTED，不透传面板 token。

桥接在当前 Invocation 内给每次有意调用分配递增事件号，先持久化本地受限队列，再用稳定键向产物服务登记 message；同一次传输重试复用键，不同调用可再次发送。通知渠道仅来自任务用户绑定；返回 registered 表示登记接受，实际 SENT/FAILED/UNKNOWN 在通知页查看，不声称用户已收到。接收回执丢失只查回执或重投，不重跑主脚本。这里去重仅覆盖桥接器对同一次登记的传输重试；脚本主动再次调用通知方法会创建新消息，桥接器不猜测是否为业务重试。进程/节点丢失且未完成登记的消息可能丢失，明确显示待确认范围；不得为了补通知自动重启 legacy。需要跨故障业务级去重时改用原生批次键与检查点。

文件采集两种方式：

- `final`：仅在主进程及子进程停止写入后，读取配置中的明确文件清单，建立 `final.<invocation_id>` 批次。文件不存在标记缺项；发生进程错误仍可按授权保存已有诊断产物，不改变业务终态。超时/取消并不保证末尾采集完成。
- `manifest`：脚本先写完整文件并关闭，再把符合 legacy-emission.schema.json 的清单从临时文件原子改名到 `/work/outputs/<manifest_dir>` 下的 `.json` 文件。每份清单显式 batch_key、output_key、相对文件路径、媒体类型、字节数和 SHA-256；同一个进程可反复交接多个批次。Runner 只消费已完成交接的清单，不按文件 mtime 或日志关键词推断产物。

两种方式均通过既有上传/批次服务登记。交接清单本身也须拒绝链接/特殊文件、限定读取目录和单份 1 MiB 上限；读取后固定清单摘要，不能再次信任同一路径被替换的内容。Runner 对文件使用受限目录句柄、拒绝链接/特殊文件、核验采集前后元数据及真实字节摘要并复制到不可变暂存；发生修改则拒绝本次交接。禁止把仍在增长的同一文件直接暴露给下载端。manifest 模式按既有 `(output_series_id,batch_key)` 幂等，同键异体冲突；每批只能出现一次 output_key，可在新批复用。

交接队列、待采字节与目录有配额和背压；产物服务不可用时有界重试，超额按 output_failure_policy 继续并报错或受控停止，不无限占用内存/磁盘。消费 ACK 查询和同键重传不产生新文件/消息。采集授权随租约检查，晚到清单不能越过撤权。普通 legacy 的文件清单不提供检查点原子提交承诺；需要该能力时用原生 SDK 的 batch+checkpoint。

### 14.3 长期兼容脚本

已有脚本可在同一专属环境内持续循环，使用 adapter manifest 清单或有限通知桥接多次产出。它沿用本文件 service/manual、短租约、滚动用量、背压和停止规则，不使用高频 Cron 反复启动。只有 final 文件采集的脚本，在进程结束前不会自动产生文件批次；界面应提示改用连续交接或原生产物 SDK。

普通 legacy 未实现标准 resume_handler 时，restart_policy=never；桥接队列只重试产物登记，不在失联后重跑整个脚本以补消息。停止先撤销新业务许可，在独立有界产物宽限期内处理已完成交接，强制结束不保证最后批次成功。阶段性产物发布不会结束 Run，也不证明业务进度正常。适配约束见 [旧脚本接入规则](#legacy)。

### 14.5 连续文件交接字段

交接对象必填adapter_protocol_version=1.0、batch_key、files。files为1～100项，每项必填output_key、path、media_type、size_bytes、sha256。path相对/work/outputs，最长256字符且限定普通文件，media_type最长128字符，size_bytes为0～104857600的整数，sha256为64位小写十六进制。一个批次内output_key唯一，文件全部完成写入后再原子交接清单。原始字节由采集方复核。

outputs的final模式指定files，每项含output_key、path和media_type。manifest模式指定manifest_dir。关闭文件采集时outputs.mode为none，关闭通知桥接时notification_bridge.mode为disabled，两者显式填入配置以固定本版本能力。

## 15. 本地桥接与公共能力

本节定义待实现的桥接线协议。各语言SDK是对同一协议的封装，也可直接用标准HTTP客户端接入。桥接只暴露在当前专属环境的回环地址，Agent管理通道使用独立身份。每次请求携带 `Authorization: Bearer <短期调用能力>`，令牌从TT_BRIDGE_TOKEN_FILE读取，字段不进入业务input或日志。

成功JSON响应采用 `{data, request_id}`，失败采用 `{error:{code,message,field_errors,retry_after_seconds},request_id}`。field_errors包含JSON Pointer路径、rule和脱敏message，缺省为空数组，retry_after_seconds可为null。HTTP状态按400结构错误、401身份失效、403授权拒绝、409幂等或状态冲突、422业务校验、429限流、503依赖不可用表达。所有POST携带Idempotency-Key，作用域为Invocation、路由及键，同体返回原回执、异体409。桥接验证当前阶段、租约和服务端授权，来路进程自报ID仅用于关联检查。下表路径均相对TT_BRIDGE_URL。

| 方法及路径 | 请求和返回 | 实施规则 |
| --- | --- | --- |
| `GET /bridge/v1/control` | 返回与控制文件一致的最新快照 | 允许有界停止期间读取 |
| `POST /bridge/v1/http` | 请求为request_key、operation_key、method、url、headers、body、timeout_ms、credential_alias、effect。body为null或{encoding:utf8/base64,value:string}。返回request_id、status、headers及同形body | 只读请求的operation_key可为null，写入或unknown须有稳定操作键。credential_alias可为null。effect取read_only/external_write/unknown。请求键同体只查原回执 |
| `GET /bridge/v1/operations/{operation_key}` | 返回{operation_key,state,request_id,response}，尚无记录时data=null，response为原HTTP回执或null | 范围绑定服务端逻辑履约或私有Run，state取REGISTERED/NOT_SENT/MAY_HAVE_SENT/RESPONSE_RECEIVED。跨接续读取原操作，保留脚本报告与出站证据的来源 |
| `POST /bridge/v1/credentials/read` | 请求{alias}，返回{name,kind,secret_payload} | 仅已声明、已绑定、当前允许脚本接触的凭据。对象字段由对应kind契约定义 |
| `POST /bridge/v1/events` | 完整script-event 2.0信封 | 核对声明、数据、事件键和调用归属，登记后由平台投递 |
| `POST /bridge/v1/progress` | {stage,cursor_summary}，返回接受回执。stage和cursor_summary为有界脱敏字符串，后者可为null | 限频及大小，保持Runner心跳独立 |
| `GET /bridge/v1/checkpoint` | 返回当前绑定范围的{checkpoint_id,revision,value,schema_digest}，无记录时data=null | 核对用户、任务、动作、版本及恢复授权 |
| `POST /bridge/v1/checkpoint` | {value,expected_revision}，首次expected_revision=0。返回新检查点回执 | 检查Schema及CAS，冲突409 |
| `POST /bridge/v1/output-batches/begin` | {output_series_id,batch_key,phase}，返回{batch_id,emission_id,state} | 建立或取得本批句柄。OUTPUT_HOOK须先由Agent完成权限阶段切换 |
| `POST /bridge/v1/outputs/uploads` | {output_key,file_name,media_type,size_bytes,sha256}，返回{upload_id,chunk_size} | 携带X-Script-Tools-Batch头绑定batch_id，为本系列预登记上传 |
| `PUT /bridge/v1/outputs/uploads/{id}/chunks/{index}` | 原始字节及内容摘要，返回分片回执 | index从0开始，同索引同字节幂等，完整字节摘要再校验 |
| `POST /bridge/v1/outputs/uploads/{id}/complete` | {sha256}，返回{upload_id,state} | 完成分片及整文件检查，state=UPLOADED后可供file引用，登记提交后再确认产物可用性 |
| `POST /bridge/v1/outputs` | 完整output.schema.json登记请求，返回OutputRef | X-Script-Tools-Batch绑定batch_id，file引用已完成upload_id，消息使用本人绑定渠道 |
| `POST /bridge/v1/output-batches` | 完整output-batch.schema.json请求及X-Script-Tools-Batch，返回批次回执 | 核对句柄、同键去重及检查点CAS，运行中Hook提交后由Agent复核并恢复业务阶段 |
| `POST /bridge/v1/result` | 完整result 2.0信封，返回{accepted:true,digest,accepted_at} | hook-bridge在动作结束后调用，必须持久化接受后才执行末尾Hook |
| `GET /bridge/v1/result/receipt` | 返回{accepted,digest,accepted_at}，未接受时后两者为null | 回执丢失时查询，补报相同结果。授权仅够读取当前Invocation回执 |

HTTP的headers采用 `{name:string,value:string}` 数组，保留重复响应头和多条Set-Cookie。桥接校验头名称、换行、目标和受控头规则。body.value、headers和响应内容都有资源预算。桥接解析base64前检查编码长度，解码后检查真实字节数。发送URL、重定向、DNS目标、凭据目标域、方法、并发及请求预算继续经过统一出口控制。Set-Cookie、Authorization和敏感响应头在日志链路脱敏，脚本可按会话逻辑保存本次允许使用的Cookie。

HTTP的request_key表示一次实际发送意图，同键重投只查询或返回该意图的原回执。需要再次发出只读查询时分配新request_key，并关联原查询。operation_key绑定跨Invocation的同一逻辑业务操作，采用第18章的受限key格式，服务端从履约及授权记录确定其作用域。网关在发送前持久登记操作键及请求摘要，已接受或未决操作的再次写入保持阻塞，异体请求返回冲突。桥接服务保存幂等记录及未决状态到可信持久层，进程重启后从该层恢复。

操作状态描述网关观测的发送事实。RESPONSE_RECEIVED仍需业务代码或已绑定核验器解析上游响应，MAY_HAVE_SENT按未知效果处理。通用平台依据动作授权、原操作记录和逻辑履约阻塞约束执行，需要跨任务核对人员、日期或其他领域目标时，由显式绑定的领域扩展提供相应归属及防重规则。

hook-bridge程序负责在同一进程中按第7章分发动作及可选Hook。结果接受后Agent切换到有界OUTPUT/诊断权限，程序查询接受回执并执行final on_outputs、after_action、on_cleanup。运行中产物Hook通过可信Agent切换权限阶段后调用。包装器声明的阶段须由Agent确认，函数名仅用于定位。invocation-files模式的文件结果采集完成后结束本次进程生命周期。

<a id="script-logging"></a>

## 16. 日志与可观测性

普通日志记录stage、耗时、计数、受限错误码和本次关联ID。HTTP日志使用域名、规范化路径及请求ID，查询串、请求体、原始响应、Token、Cookie、联系人和证件字段按敏感策略处理。异常对象的字符串和堆栈同样进入脱敏链路。

自定义事件在manifest.events声明，用稳定event_key去重。通知由用户订阅或message产物触发，渠道从本人任务绑定读取。产物保存文本、JSON、文件或消息，通过批次登记获得OutputRef。结果引用已接受产物ID，完整历史通过产物API查询。文件采用明确白名单，临时配置和会话材料按临时数据生命周期清理。

相同逻辑产出使用相同batch_key及output_key。新批次代表一次新产出，可在运行中多次提交。需要产物与进度一致时使用批次加检查点原子提交。结果、产物可用性和消息投递分别保存回执。

```python
import json
import os
import tempfile
from pathlib import Path


def main():
    invocation = json.loads(Path(os.environ["TT_INVOCATION_PATH"]).read_text(encoding="utf-8"))
    if invocation["action"] != "hello" or invocation["input"] != {}:
        raise ValueError("Unsupported invocation")
    result = {
        "protocol_version": "2.0",
        "run_id": invocation["run_id"],
        "attempt_id": invocation["attempt_id"],
        "invocation_id": invocation["invocation_id"],
        "action": invocation["action"],
        "outcome": "COMPLETED",
        "data": {"message": "hello"},
        "action_required": None,
        "error": None,
        "outputs": [],
    }
    target = Path(invocation["output_path"])
    descriptor, temporary = tempfile.mkstemp(prefix=".result-", dir=target.parent)
    try:
        with os.fdopen(descriptor, "w", encoding="utf-8") as stream:
            json.dump(result, stream, ensure_ascii=False, allow_nan=False)
            stream.flush()
            os.fsync(stream.fileno())
        os.replace(temporary, target)
    finally:
        Path(temporary).unlink(missing_ok=True)


if __name__ == "__main__":
    main()
```

```javascript
import { open, readFile, rename, unlink } from "node:fs/promises";
import { randomUUID } from "node:crypto";
import path from "node:path";

const invocation = JSON.parse(await readFile(process.env.TT_INVOCATION_PATH, "utf8"));
if (invocation.action !== "hello" || invocation.input === null ||
    Array.isArray(invocation.input) || typeof invocation.input !== "object" ||
    Object.keys(invocation.input).length !== 0) {
  throw new Error("Unsupported invocation");
}
const result = {
  protocol_version: "2.0",
  run_id: invocation.run_id,
  attempt_id: invocation.attempt_id,
  invocation_id: invocation.invocation_id,
  action: invocation.action,
  outcome: "COMPLETED",
  data: { message: "hello" },
  action_required: null,
  error: null,
  outputs: [],
};
const target = invocation.output_path;
const temporary = path.join(path.dirname(target), `.result-${randomUUID()}`);
try {
  const stream = await open(temporary, "wx", 0o600);
  try {
    await stream.writeFile(JSON.stringify(result), "utf8");
    await stream.sync();
  } finally {
    await stream.close();
  }
  await rename(temporary, target);
} finally {
  await unlink(temporary).catch((error) => {
    if (error.code !== "ENOENT") throw error;
  });
}
```

## 18. 契约字段与兼容要求

本章补齐开发者直接构造事件、产物和批次时使用的字段。所有对象使用协议定义的字段，业务data及input按发布者Schema校验。未知协议字段在结构校验时拒绝，业务额外字段由相应Schema决定。

### 18.1 版本与字段约束

| 对象 | 协议版本 | 必需字段及约束 |
| --- | --- | --- |
| Manifest | 2.0 | schema_version、script_id、version、language、entrypoint、integration_mode、default_action、actions、dependencies_lock、credential_requirements、network_requirements、supported_execution_modes、input_schema，hooks模式另需hook_protocol_version=2.0 |
| Invocation | 2.0 | protocol_version、run_id、attempt_id、invocation_id、script_version_id、action、context、input、runtime、credential_bindings、output_path |
| Result | 2.0 | protocol_version、run_id、attempt_id、invocation_id、action、outcome、data、action_required、error。summary及outputs可选 |
| ScriptEvent | 2.0 | protocol_version、run_id、attempt_id、invocation_id、script_version_id、event_name、event_key、data |
| Output | 2.0 | protocol_version、output_key、kind、payload，title可选且最多200字符 |
| OutputBatch | 2.0 | protocol_version、batch_key、phase、outputs、producer_outcome、producer_error、output_series_id、reason，checkpoint可选 |
| LegacyAdapter / Emission | 1.0 | 适配映射与文件交接独立协商，完整字段见第14章及本章 |
| Manifest扩展 / Runtime | 2.1 / 1.0草案 | 清单增加runtime_spec，运行描述含runtime_protocol_version、runtime_profile_id、platform及launch，build可选 |

动作、事件、批次及产物key使用 `[A-Za-z_][A-Za-z0-9_.-]{0,127}`。script_id、version及运行关联ID为1～128字符字符串。handler采用 `[A-Za-z_][A-Za-z0-9_.]*`。entrypoint与dependencies_lock为最长256字符的受控包内路径。summary最多2000字符，error.code为1～128字符，error.message最多1000字符，details可为受限对象。event_key为1～200字符字符串。时间采用带时区RFC3339字符串，平台信封使用UTC。

credential_requirements条目含name、kind、required，name和kind各为1～128字符。credential_bindings条目含requirement、credential_version_id。network_requirements含mode、domains、methods，mode取HTTP/BROKER/PROXY，methods采用GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS。允许域名及凭据解密最终以实际授权为准。

### 18.2 产物登记与批次

| kind | payload字段 |
| --- | --- |
| text | content字符串、media_type为text/plain或text/markdown |
| json | data为任意合法JSON |
| file | upload_id、file_name、media_type、size_bytes、sha256。上传完成后使用平台回执，文件名最长200字符，SHA-256采用64位小写十六进制 |
| message | title、body、format、channel_binding_ids、attachments，format为text/plain或text/markdown，attachments条目为{output_id} |

OutputRef结构为 `{output_id:string}`。文件名采用单一文件名，路径由平台内部管理。message的channel_binding_ids为1～10个本人已绑定ID，attachments最多10项。Result.outputs和OutputBatch.outputs最多100项，均使用OutputRef。批次phase取ACTION或OUTPUT_HOOK，reason取explicit/interval/checkpoint/final，producer_outcome取COMPLETED/FAILED/TIMED_OUT/CANCELLED。COMPLETED时producer_error=null，其余为{code,message}。checkpoint含value和expected_revision，首次revision为0。批次提交前先通过SDK或桥接建立批次句柄。

### 18.3 兼容和交付

版本input_schema始终必填，动作input_schema完整覆盖版本定义。每个hooks动作声明handler、side_effects和output_schema，resume_actions只引用本版本已有动作。恢复入口resume_handler需要checkpoint_schema，安全恢复还需平台能力与本次策略允许。所有可选Hook必须与封存代码中的可调用入口对应。

本文内嵌JSON样例可直接保存为文件，示例ID及时间在实际派发时由平台生成。平台接入方随校验工具提供manifest、invocation、result、script-event、output、output-batch及legacy相关机器Schema，工具必须与正文协议版本一致。新版本通过固定版本选择及能力协商启用，存量封存版本按绑定协议执行。

3. 保存第17章对应语言代码为main.py或main.mjs，构造action=hello、input={}的调用文件，其余关联字段使用第6章信封结构，output_path指向本地临时目录中的result.json。

6. 在平台指定的运行配置中进行隔离构建和授权试运行，确认manifest声明的每项能力实际可用后封存版本。

每次修改业务规则、依赖、Schema或执行配置形成新版本。开发者标明兼容变化和迁移输入，平台由用户选择升级并重新确认授权。售卖服务还需填写一次服务执行包含哪些接续、交付目标和未达目标处理规则。

person_id选择是需要新增的封装逻辑。当前choose_persons按证件或姓名匹配，不能把新的person_ids字段直接交给旧函数。封装层选出每位人员后，使用其原始对象调用planner，并将按person_id配置的票种、年龄及学生覆盖转换为planner接受的本次映射。缺失、重复或超出授权的人员使校验失败，保留精确选择范围。

第20.8节内嵌的完整清单定义了日期、时段、person_ids、联系人、票种覆盖和最高票款。maxItems等数值是样例包的输入预算，上游场次人数限制在运行时另校验。`max_ticket_fee_minor=0`明确只接受免费票方案，正数表示用户允许的总票款上限，currency固定CNY。

脚本源码包含收费及免费票的金额处理和待支付链接。平台接入时按实际票种和用户授权检查金额。脚本服务费由购买订单固定，景点票款按上游订单事实单独展示。预约动作发现票款大于授权上限时返回脱敏错误并停止提交。

tiananmen_session为本方案待登记的凭据kind。目标secret_payload结构为 `{token:string,upstream_user_id:string,cookies:{JSESSIONID?:string,wzws_sid?:string}}`，字段采用非空字符串并限制长度。封装层查询logininfo后核对upstream_user_id，账号不一致时要求本人重新绑定。Cookie轮换只更新本次专属会话，需要跨调用保存的新凭据通过受控凭据版本流程写入。JWT中的exp可用于提示到期，实际认证以授权和上游登录态检查为准。

### 20.4 提交、查询和结果映射

| 观测情况 | 脚本返回 | 平台后续处理 |
| --- | --- | --- |
| 预览完成 | COMPLETED，data包含脱敏候选及预计票款 | 展示方案，等待正式运行授权 |
| 窗口结束，始终无可用方案且从未提交 | COMPLETED，booking_state=NO_AVAILABILITY | 记录目标未达，按已购规则处理履约 |
| 提交接口受理并取得taskId | 持久化SUBMITTED，查询该taskId | 阻止同一意图再次下单 |
| 查询取得订单号及状态 | data为ORDER_FOUND，保存上游状态和金额 | 脚本报告可展示，领域核验按扩展执行 |
| 已知订单需要用户支付或其他外部操作 | ACTION_REQUIRED / EXTERNAL_ACTION，data保留ORDER_FOUND，resume_action=query_order | 展示受校验官方入口，接续只读查询。期限取有效渠道证据 |
| 下单可能已发送，响应超时、破损或无taskId | ACTION_REQUIRED / MANUAL_RESOLUTION，booking_state=UNKNOWN，resume_action=query_order | 保存出站证据并保留防重阻塞，进行已授权核验 |
| 只有taskId，查询期限内没有订单结论 | ACTION_REQUIRED / MANUAL_RESOLUTION，data保留SUBMITTED及taskId | 后续查询原task，保留未决事实 |
| 提交前凭据失效 | ACTION_REQUIRED / CREDENTIAL_UPDATE，data为NOT_SUBMITTED，已有查询ID时resume_action=query_order，其余为null | 更新后先核对已有操作。确认未执行后由用户显式创建后续授权调用 |
| 确定无副作用的参数拒绝 | ERROR，明确错误码及脱敏路径 | 修正输入后按平台流程重新发起 |

查询不到订单时还须考虑上游异步处理和查询可见性。只有上游证据足够证明未执行时，才可解除相应阻塞。样例query_order使用已有taskId或订单号查询。没有任何上游ID的UNKNOWN保留人工处理，后续可在实现授权范围内的订单列表匹配后扩展核验能力。

query_order的输入ID必须与该逻辑履约已登记的出站证据关联，并使用同一授权账号查询。恢复页面传入ID仍由平台复核归属。发送了预约写入后发生401、取消或租约中断，也按原操作是否未决决定后续查询及待处理。

### 20.5 封装层执行顺序

1. 读取Invocation，校验action、完整input、凭据绑定、授权和当前期限。
2. 取得本次允许使用的会话，构造内存Config和受控transport，关闭原token_auth.command路径。
3. 在受控HTTP预算内校验登录态，读取人员、票种和场次，精确筛选person_ids，调用planner构造方案。
4. preview_booking返回脱敏方案。query_order只查询已登记外部操作。book继续执行以下步骤。
5. 查询本逻辑履约的历史意图和外部订单。存在未决写入时查询原操作。确认可提交时固定目标、人员、金额摘要及稳定操作键。
6. 通过受控网关登记并发出createTicketOrder。把接受回执、taskId或UNKNOWN证据持久化，再决定查询或待处理。
7. 有taskId时调用task_status，在取消、租约和期限内进行有界查询。存在orderid时获取其状态，保存票款及用户需要完成的外部操作。
8. 提交符合output_schema的最终结果，查询结果接受回执，随后生成有权限的脱敏产物，完成清理。

需要修改的核心接口是可注入的transport、取消等待、结构化进度及操作证据存储。复用planner和已还原的API解析逻辑。平台归属、权益、待处理及可信核验由对应服务保存。

### 20.7 设计模式在预约脚本中的落地

建议先按下表调整模块边界，再接入平台运行。planner中的纯函数可直接复用，平台入口与本地CLI分别组装同一套业务服务和依赖。

| 建议模块 | 模式或职责 | 对现有脚本的具体改动 |
| --- | --- | --- |
| platform_entry.py | 适配器、动作注册表 | 从Invocation构建只读输入，将preview_booking/book/query_order映射到业务函数，统一返回信封 |
| booking_service.py | 应用编排、依赖注入 | 从AccountWorker提取prepare、submit、resolve的业务顺序，构造时注入provider、operations、clock、wait、logger |
| transport.py | HTTP适配器 | 本地实现接requests，平台实现接受控网关，sync_clock也通过同一接口 |
| planner.py | 业务纯函数、可选策略 | 保留年龄和票种计算，确有多种选择方案时注入策略函数，person_id先精确映射为已授权人员 |
| booking_state.py | 显式状态机 | 定义下表转换函数，集中处理taskId、orderid、未知效果和支付待处理 |
| operation_store.py | 小型仓储接口 | 对接平台操作查询及检查点，恢复读取既有回执，使用稳定operation_key |
| presentation.py | 结果映射 | 把状态转换为data、outcome、action_required，集中处理脱敏摘要及事件 |

文件划分可随脚本规模合并。首先完成transport注入、状态转换和取消等待，再按实际重复代码提取策略。处理函数、生命周期Hook和平台部署服务各自按已声明契约调用。

| 当前booking_state | 新证据 | 转换及后续动作 |
| --- | --- | --- |
| NOT_SUBMITTED | 目标可用、授权有效、操作登记成功 | 执行一次受控提交，立即记录请求效果 |
| NOT_SUBMITTED | 返回有效taskId | SUBMITTED，持久化taskId并查询原任务 |
| NOT_SUBMITTED | 可能已发送且回执不完整 | UNKNOWN，保存请求关联，进入核验或待处理 |
| NOT_SUBMITTED | 窗口结束且已证明从未提交 | NO_AVAILABILITY，按实际业务目标返回结果 |
| SUBMITTED | 查到匹配的orderid | ORDER_FOUND，分别保存上游订单状态、票款和外部待处理 |
| SUBMITTED | 查询仍排队或暂时不可见 | 保持SUBMITTED，按期限有界查询，期限结束后转待处理 |
| UNKNOWN | 查到相同授权目标的订单证据 | ORDER_FOUND，保留原未知记录及本次查询来源 |
| UNKNOWN | 查询无记录或结果含糊 | 保持UNKNOWN及防重阻塞 |
| UNKNOWN | 已授权核验明确证明未执行 | 由平台解除对应阻塞，后续提交需有效授权及明确执行指令 |
| ORDER_FOUND | 用户仍需支付或完成其他操作 | 保持ORDER_FOUND，用EXTERNAL_ACTION描述待处理，接续查询原订单 |

状态转换函数只计算下一状态及待执行步骤，操作记录和检查点通过注入接口持久化。调用超时到UNKNOWN的路径必须测试，多个任务的操作归属及防重由平台记录复核。整个外部写入不放入统一自动重试装饰器。
